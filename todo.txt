- The cfg_man library shouldn't output to stdout: the client should pass a callback function
  with a prototype similar to printf (dependency injection.  This makes the library more portable
  and simplifies testing.

- Tests are now dependent on the library, so the test Makefile doesn't
  need to generate CUT dependencies anymore.
- Optionally, save NVRAM not as TLV, but as text -- the same text produced on
  command "prt", or a YAML configuration file.
  o Parsing the YAML file should be much the same as parsing an input command.
    We re-use the print function to print the value to the YAML file,
    and re-use the set function to set the RAM based on the YAML text.

- Extend utils to unsigned int, strings, hexstrings, etc.
- Can we avoid saving the unused parts of strings to TLV?  Descriptor could
  contain a ptr for a getLen fn, which is NULL in most cases, but the user could
  install strlen for strings.  If NULL, the default is to use the full length of the item
  from the descriptor.

- Having an ID in a counter descriptor is not needed, since it's not saved to TLV.
  The same applies to any non-persistent items like stats, that are not saved 
  in NVRAM.
- Provide context-sensitive help in a way that could be used for "tabbing out" input strings.
  Step 1: respond to inputs without a carriage return.
- Strategy for making fewer methods public: do we need friends, or interface classes...
- Make C-friendly: a C-friendly wrapper?
- Verify ROM-ability of meta-data, which is const.
  An easy way to achieve ROMability would be to place the things we want in
  ROM, in plain old structs, which we make const and init at compile-time.  This would probably
  only mean we'd have one additional level of indirection, but few other negative effects.
  Probably my classes derived from cm_item_descriptor, although all data
  is const, are no ROMable, since they are derived classes, with constructors, etc.
  Possibly ROMable classes are easier to identify than I thought -- they 
  can be initialized like C structures: struct x = {};
  what data is allocated to which memory address ranges.
- Should I be using malloc, or new?
- Is there superfluous info in the TLV files?  At least for simple types, if I know the type
  I already know the length.  What do we do if a simple item's size is not what's expected?
  We should just discard it: At least for big-endian systems, correct truncation would depend 
  on knowing if the item is an integer or a character array (string or hex string)

- Separation between TLV and its client: one of the goals is that we could easily
  substitute another way of saving the data, other than TLV.  The most obvious 
  alternative is to save the data in text format, exactly the same format that
  we print to the console.
  Preferably we should have more modules, instead of the current 2 (client and TLV):
  1. client
  2. formatter, that knows TLV or other data format to be stored to NVRAM
  3. NVRAM, that knows how to read, write and skip through a file.
  4. Perhaps abstraction of file access at the lowest level, if only to simplify unit
     testing.
